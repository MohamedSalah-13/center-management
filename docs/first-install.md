# دليل التركيب الأول

خطوات تجهيز النظام على جهاز جديد — سواء جهاز تطوير أو أول تركيب عند عميل.

> **لا توجد سكربتات ترحيل في هذا المشروع.** التركيب الجديد يبدأ بقاعدة بيانات فارغة
> ينشئها Hibernate بالأنواع الصحيحة. راجع القسم الأخير لو احتجت يوماً ترحيل قاعدة
> بيانات قائمة فيها بيانات.

---

## 1. المتطلبات

| المكوّن | النسخة | ملاحظة |
|---|---|---|
| Java | 21 | يجب أن يكون `java -version` يشير إليها |
| MySQL | 8.0+ | |
| Maven | 3.9+ | للبناء فقط، غير مطلوب على جهاز العميل |
| `mysqldump` و `mysql` | مع MySQL | **يجب أن يكونا في `PATH`** وإلا لن تعمل النسخ الاحتياطية |

للتأكد من الأخير:

```bash
mysqldump --version
```

## 2. إنشاء قاعدة البيانات ومستخدم مخصّص لها

**لا تستخدم `root` للتطبيق.** التطبيق يتصل بقاعدة البيانات مباشرةً من جهاز المستخدم،
فبيانات الاتصال ستكون على ذلك الجهاز حتماً. لا يمكن إخفاؤها إخفاءً حقيقياً، والحماية
الفعلية هي تضييق ما تستطيع فعلها لا إخفاؤها.

نفّذ داخل MySQL كمسؤول:

```sql
CREATE DATABASE center_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER 'center_app'@'localhost' IDENTIFIED BY 'ضع-كلمة-قوية-مختلفة-لكل-تركيب';

GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
  ON center_db.* TO 'center_app'@'localhost';

FLUSH PRIVILEGES;
```

`CREATE` و `ALTER` مطلوبتان لأن `ddl-auto=update` ينشئ الجداول ويحدّثها. لا تمنح
`GRANT OPTION` ولا صلاحيات على قواعد بيانات أخرى.

> لو كان السنتر يشغّل النظام على أكثر من جهاز عبر الشبكة، استبدل `localhost`
> بنطاق الشبكة (مثل `'center_app'@'192.168.1.%'`) وامنح كل جهاز نفس الصلاحيات
> المحدودة. لا تفتح المنفذ 3306 على الإنترنت.

## 3. ضبط بيانات الاتصال

بيانات الاتصال **ليست في المستودع** ولا قيمة افتراضية لكلمة المرور، فالتطبيق لن يعمل
بدون ضبطها. اختر إحدى الطريقتين:

### الطريقة أ — ملف إعدادات محلي (الأنسب للتطوير)

أنشئ `src/main/resources/application-local.properties` — وهو مستثنى من git بالفعل:

```properties
spring.datasource.username=center_app
spring.datasource.password=الكلمة-التي-وضعتها
```

ثم شغّل بالبروفايل `local`.

### الطريقة ب — متغيرات بيئة (الأنسب للتركيب عند العميل)

على ويندوز، من طرفية بصلاحيات المستخدم نفسه:

```bash
setx DB_USERNAME "center_app"
```

```bash
setx DB_PASSWORD "الكلمة-التي-وضعتها"
```

`setx` تحفظ القيمة دائماً لحساب المستخدم. انتبه لأمرين: القيمة تُخزَّن في سجل ويندوز
بنص صريح ويقرأها أي برنامج يعمل بنفس الحساب، والمتغيرات الجديدة **لا تصل للطرفيات
المفتوحة حالياً** فافتح طرفية جديدة بعدها.

المتغيرات المدعومة: `DB_URL` (اختياري، له قيمة افتراضية تشير إلى
`localhost:3306/center_db`) و `DB_USERNAME` و `DB_PASSWORD`.

## 4. أول تشغيل

عند أول تشغيل يحدث أمران تلقائياً:

**تُنشأ الجداول** من الكيانات بأنواعها الصحيحة — المبالغ `DECIMAL(12,2)` وليست
`DOUBLE`. لا حاجة لأي سكربت.

**يُنشأ حساب المدير** باسم `admin`. كلمة المرور **ليست ثابتة**:

- إن ضبطت `ADMIN_INITIAL_PASSWORD` قبل التشغيل تُستخدم قيمتها.
- وإلا تُولَّد كلمة عشوائية وتُطبع في الطرفية داخل إطار واضح **مرة واحدة فقط**.

سجّل الكلمة فوراً، ادخل بها، ثم غيّرها من شاشة إدارة المستخدمين. لن تُعرض ثانيةً.

## 5. الإعدادات بعد الدخول

من شاشة الإعدادات:

- **اسم السنتر ورقم الهاتف والشعار** — تظهر في التقارير والإيصالات.
- **مسار النسخ الاحتياطي** — مجلد موجود فعلاً ولمستخدم ويندوز صلاحية الكتابة فيه.
- **تفعيل النسخ التلقائي** — يشغّل مهمة يومية الساعة 2 صباحاً. تعتمد على وجود
  `mysqldump` في `PATH`، فتأكد من الخطوة 1. **الجهاز يجب أن يكون شغّالاً في ذلك
  الوقت** وإلا لن تُؤخذ النسخة؛ لا يوجد تعويض عن موعد فائت.

خذ نسخة احتياطية يدوية مرة واحدة للتأكد من أن المسار والصلاحيات سليمة قبل الاعتماد
على النسخ التلقائي.

---

## 6. رصيد الطلاب — نقطة مهمة قبل التشغيل الفعلي

النظام يعمل بنموذج رصيد: الطالب يدفع في الخزينة فيزيد رصيده، وتُخصم رسوم الحصة عند
تسجيل حضوره على البوابة. **البوابة ترفض الدخول إذا لم يكفِ الرصيد.**

على تركيب جديد يبدأ كل الطلاب برصيد صفر، وهذا هو الصحيح: لا حصص محضورة ولا دفعات.
احرص على تحصيل الاشتراكات من شاشة الخزينة قبل أول يوم دراسي، وإلا سيُرفض كل الطلاب
على البوابة.

حقل `ledger_start_date` في جدول `center_settings` يُترك فارغاً (`NULL`) في التركيب
الجديد، ومعناه «احتسب كل الحركات». لا تلمسه إلا في حالة الترحيل الموصوفة أدناه.

## 7. لو احتجت يوماً ترحيل قاعدة بيانات قائمة

ينطبق فقط لو كانت لديك قاعدة بيانات أُنشئت بنسخة **قديمة** من البرنامج، أي أعمدة
المبالغ فيها `DOUBLE` وبها بيانات حقيقية لا يمكن حذفها.

اقرأ هذه التحذيرات قبل كتابة أي `ALTER`:

**أوامر DDL في MySQL تُحدث commit ضمنياً.** لا يمكن لفّها في transaction والتراجع
عنها. لو نجح أمر وفشل التالي تبقى القاعدة في حالة نصف مُرحَّلة، فالنسخة الاحتياطية
هي وسيلة الرجوع الوحيدة.

**تغيير `DOUBLE` إلى `DECIMAL` يعيد بناء الجدول كاملاً** ويأخذ قفلاً يمنع الكتابة
طوال العملية. **أغلق البرنامج على كل الأجهزة** قبل البدء، ونفّذ خارج ساعات العمل.

**`ADD COLUMN IF NOT EXISTS` غير مدعومة في MySQL** (صياغة MariaDB). افحص وجود العمود
باستعلام على `INFORMATION_SCHEMA` قبل الإضافة.

**القيم المخزَّنة كـ `DOUBLE` تحمل انحرافاً**، والتحويل إلى `DECIMAL(12,2)` يقرّبها.
راجع الأرصدة والإجماليات بعد الترحيل وقارنها بما قبله.

**الدفعات القديمة ليست لها قيود خصم مقابلة**، لأن نموذج الرصيد لم يكن موجوداً. لو
احتُسبت كما هي ظهر كل طالب دائناً بمبلغ وهمي كبير ودخل مجاناً. اضبط
`center_settings.ledger_start_date` على تاريخ بدء العمل بالنظام الجديد لتصفير ما
قبله، وابدأ التحصيل من جديد.

الخطوات بالترتيب:

```bash
mysqldump -u center_app -p center_db > before_migration.sql
```

ثم أغلق البرنامج على كل الأجهزة، ثم نفّذ التعديلات على `transactions.amount` و
`course_groups.session_price` و `teachers.commission_value`، ثم أضف
`ledger_start_date` واضبطه، ثم تحقق:

```sql
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = 'center_db'
  AND COLUMN_NAME IN ('amount', 'session_price', 'commission_value');
```

يجب أن تظهر الثلاثة `decimal(12,2)`.

## 8. ملاحظة معمارية

`ddl-auto=update` يبني الجداول ويضيف الأعمدة، لكنه **لا يغيّر أنواع الأعمدة الموجودة
ولا يحذف شيئاً**. هو مقبول ما دام النظام لم يُوزَّع على عملاء متعددين، لكنه لا يصلح
لإدارة تطوّر المخطط عبر تركيبات مختلفة.

قبل التوزيع على أكثر من عميل، انقل المشروع إلى **Flyway** أو **Liquibase**: تصبح كل
تغييرة في المخطط ملفاً مُرقَّماً يُنفَّذ مرة واحدة ويُسجَّل، فتعرف أي تركيب على أي
نسخة، ويختفي الترحيل اليدوي الموصوف في القسم 7 من الأساس.
