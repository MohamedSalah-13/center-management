# دليل التركيب الأول

خطوات تجهيز النظام على جهاز جديد — سواء جهاز تطوير أو أول تركيب عند عميل.

> **المخطط تديره Flyway.** أول تشغيل ينشئ الجداول تلقائياً من ملفات الترحيل في
> `db/migration`، ولا حاجة لتنفيذ أي شيء يدوياً. القسم 7 يشرح ما يلزم لو كانت لديك
> قاعدة بيانات أُنشئت بنسخة قديمة من البرنامج قبل اعتماد Flyway.

## 2. إنشاء قاعدة البيانات ومستخدم مخصّص لها

**لا تستخدم `root` للتطبيق.** التطبيق يتصل بقاعدة البيانات مباشرةً من جهاز المستخدم،
فبيانات الاتصال ستكون على ذلك الجهاز حتماً. لا يمكن إخفاؤها إخفاءً حقيقياً، والحماية
الفعلية هي تضييق ما تستطيع فعلها لا إخفاؤها.

### ⚠️ أولاً: حدّد النطاق الصحيح للمستخدم

في MySQL الصلاحية مرتبطة بـ **المستخدم والعنوان الذي يتصل منه** معاً. `'center_app'@'localhost'`
لا يقبل اتصالاً قادماً من عنوان آخر، والنتيجة تكون:

```
Access denied for user 'center_app'@'<عنوان ما> (using password: YES)
```

اختر النطاق حسب مكان تشغيل MySQL:

| مكان تشغيل MySQL | النطاق الصحيح |
|---|---|
| مثبَّت على نفس الجهاز | `'center_app'@'localhost'` |
| **داخل حاوية Docker** | `'center_app'@'%'` |
| على خادم في شبكة السنتر | `'center_app'@'192.168.1.%'` (نطاق شبكتك) |

**حالة Docker تحديداً مربكة:** `localhost` داخل الحاوية تعني الحاوية نفسها، لا جهازك.
التطبيق يعمل على ويندوز فيصل اتصاله إلى الحاوية عبر بوابة Docker بعنوان مثل
`172.17.0.1`، فلا يطابق `localhost` ويُرفض. لاحظ أن الدخول بـ `root` ينجح رغم ذلك،
لأن صورة MySQL الرسمية تُنشئ `root@'%'` — فنجاح `root` لا يعني أن الإعداد سليم.

مع Docker، ادخل من داخل الحاوية لتنفيذ الأوامر التالية:

```bash
docker exec -it <اسم-الحاوية> mysql -u root -p
```

### الأوامر

```sql
CREATE DATABASE center_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

-- استبدل '%' بالنطاق المناسب من الجدول أعلاه
CREATE USER 'center_app'@'%' IDENTIFIED BY 'ضع-كلمة-قوية-مختلفة-لكل-تركيب';

GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES
  ON center_db.* TO 'center_app'@'%';

FLUSH PRIVILEGES;
```

`CREATE` و `ALTER` و `DROP` مطلوبات لأن Flyway تنشئ الجداول وتعدّلها في ملفات الترحيل،
و**الاستعادة من نسخة احتياطية تستبدل الجداول فتحذفها أولاً**. كلها مقصورة على
`center_db` وحدها. لا تمنح `GRANT OPTION` ولا `SUPER` ولا `PROCESS` ولا أي صلاحية على
قواعد بيانات أخرى.

> **تركيب قائم بلا `DROP`؟** ستفشل الاستعادة بالخطأ
> `1142 … DROP command denied`. أضفها بمستخدم root مرة واحدة:
>
> ```sql
> GRANT DROP ON center_db.* TO 'center_app'@'%';
> FLUSH PRIVILEGES;
> ```
>
> مع Docker نفّذها من داخل الحاوية كما في الأمر أعلاه. وانتبه إلى أن الصلاحيات مربوطة
> بالمضيف: مستخدم أُنشئ لـ `'center_app'@'localhost'` لا تنفعه منحة كُتبت لـ `'%'`.
> اقرأ المضيف الحقيقي من رسالة الخطأ نفسها.

للتأكد مما أُنشئ فعلاً:

```sql
SELECT user, host FROM mysql.user WHERE user = 'center_app';
```

> **`'%'` يعني «من أي عنوان».** لو كانت الحاوية تنشر المنفذ على `0.0.0.0:3306`
> فأي جهاز على الشبكة يصل لقاعدة البيانات، وكلمة المرور هي الحاجز الوحيد. على جهاز
> تطوير قيّد النشر على الجهاز نفسه: `docker run -p 127.0.0.1:3306:3306 ...`
> ولا تفتح المنفذ 3306 على الإنترنت في أي حال.

## 3. ضبط بيانات الاتصال

بيانات الاتصال **ليست في المستودع** ولا قيمة افتراضية لكلمة المرور، فالتطبيق لن يعمل
بدون ضبطها. اختر إحدى الطريقتين:

### الطريقة أ — ملف إعدادات محلي (الأنسب للتطوير)

أنشئ `src/main/resources/application-local.properties` — وهو مستثنى من git بالفعل:

```properties
spring.datasource.username=center_app
spring.datasource.password=الكلمة-التي-وضعتها
```

ثم شغّل بالبروفايل `local`.

### الطريقة ب — متغيرات بيئة (الأنسب للتركيب عند العميل)

على ويندوز، من طرفية بصلاحيات المستخدم نفسه:

```bash
setx DB_USERNAME "center_app"
```

```bash
setx DB_PASSWORD "الكلمة-التي-وضعتها"
```

`setx` تحفظ القيمة دائماً لحساب المستخدم. انتبه لأمرين: القيمة تُخزَّن في سجل ويندوز
بنص صريح ويقرأها أي برنامج يعمل بنفس الحساب، والمتغيرات الجديدة **لا تصل للطرفيات
المفتوحة حالياً** فافتح طرفية جديدة بعدها.

المتغيرات المدعومة: `DB_URL` (اختياري، له قيمة افتراضية تشير إلى
`localhost:3306/center_db`) و `DB_USERNAME` و `DB_PASSWORD`.

## 4. أول تشغيل

عند أول تشغيل يحدث أمران تلقائياً:

**تُنشأ الجداول** بواسطة Flyway من ملفات الترحيل في `db/migration`، بأنواعها الصحيحة —
المبالغ `DECIMAL(12,2)` وليست `DOUBLE`. لا حاجة لتنفيذ أي شيء يدوياً.

بعدها يتحقق Hibernate من تطابق المخطط مع الكيانات (`ddl-auto=validate`) ويرفض بدء
التشغيل عند أي اختلاف. رسالة الخطأ تذكر الجدول والعمود، ومعناها أن ملف ترحيل ناقص.

**يُنشأ حساب المدير** باسم `admin`. كلمة المرور **ليست ثابتة**:

- إن ضبطت `ADMIN_INITIAL_PASSWORD` قبل التشغيل تُستخدم قيمتها.
- وإلا تُولَّد كلمة عشوائية وتُطبع في الطرفية داخل إطار واضح **مرة واحدة فقط**.

سجّل الكلمة فوراً، ادخل بها، ثم غيّرها من شاشة إدارة المستخدمين. لن تُعرض ثانيةً.

## 5. الإعدادات بعد الدخول

من شاشة الإعدادات:

- **اسم السنتر ورقم الهاتف والشعار** — تظهر في التقارير والإيصالات.
- **مسار النسخ الاحتياطي** — مجلد موجود فعلاً ولمستخدم ويندوز صلاحية الكتابة فيه.
- **تفعيل النسخ التلقائي** — ثم اختر الموعد: يومياً أو أسبوعياً (بيوم من الأسبوع) أو
  شهرياً (بيوم من الشهر)، والساعة والدقيقة. الافتراضي يومياً 2 صباحاً كما في النسخ
  السابقة. الشاشة تعرض موعد النسخة القادمة كما سيحسبه البرنامج فعلاً.
- **عدد النسخ المحفوظة** — بعد كل نسخة ناجحة تُحذف أقدم النسخ حتى يبقى هذا العدد.
  الصفر يعني الاحتفاظ بالكل، وحينها راقب مساحة القرص بنفسك.

لو كان الجهاز مطفأً في الموعد تُؤخذ النسخة بعد دقائق من أول تشغيل تالٍ، فلا يضيع
الموعد كما كان يحدث سابقاً. وسطر **"آخر نسخة تلقائية"** في الشاشة هو ما يكشف نسخاً
تفشل ليلة بعد ليلة: إن ظهر بجانبه "فات موعدها" فالنسخ لا تعمل، وسبب الفشل يظهر كاملاً
عند الضغط على "أخذ نسخة احتياطية الآن".

### التشفير

ملف النسخة نصّ صريح فيه أسماء الطلاب وأرقام أولياء الأمور وكل حركات الخزينة، وهو الملف
الذي يُنسخ عادةً على فلاشة أو إلى تخزين سحابي. **فعّل التشفير** واضبط كلمة مرور (8 حروف
على الأقل) ليصبح الملف غير مقروء لمن لا يملكها.

- كلمة المرور تُحفظ **على الجهاز** لا في قاعدة البيانات — فلو حُفظت فيها لخرج المفتاح
  داخل النسخة نفسها، ولضاع مع القاعدة يوم تحتاج الاستعادة. اضبطها على كل جهاز يأخذ نسخاً.
- **اكتب كلمة المرور في مكان آمن خارج الجهاز.** من فقدها فقد كل نسخة شُفِّرت بها؛ لا يوجد
  أي سبيل لفكّها بدونها.
- الملف المشفَّر ينتهي بـ `.sql.enc`، وشاشة الاستعادة تكتشفه وتسأل عن كلمة المرور وحدها
  دون أن تلمس قاعدة البيانات قبل التحقق منها.

### لو لم تكن أدوات MySQL في `PATH`

مثبِّت MySQL على ويندوز لا يضيفها إلى المسار افتراضياً. إما أن تضيفها (الخطوة 1)، أو
تضبط مجلدها في متغير بيئة:

```
CENTER_BACKUP_MYSQL_BIN_DIR=C:\Program Files\MySQL\MySQL Server 8.0\bin
```

خذ نسخة احتياطية يدوية مرة واحدة للتأكد من أن المسار والصلاحيات سليمة قبل الاعتماد
على النسخ التلقائي. رسالة الفشل تذكر سبب الفشل من الأداة نفسها.

### الخطأ 1044 عند سطر داخل الملف

`Error 1044 (42000) at line 42: Access denied for user 'center_app'@'%' to database 'center_db'`

الصلاحيات سليمة والملف قديم: النسخ المأخوذة بإصدارات سابقة تحوي أوامر `LOCK TABLES`
حول صفوف كل جدول (خيار `--add-locks` المفعَّل افتراضياً في `mysqldump`)، وتنفيذها يتطلب
صلاحية `LOCK TABLES` التي لا يملكها المستخدم — ولا يحتاجها لشيء آخر. النسخ الجديدة
تُؤخذ بـ `--skip-add-locks` فلا تحوي هذه الأوامر.

**الحل:** خذ نسخة جديدة بالإصدار الحالي واستعدها. ولإصلاح ملف قديم تحتاجه فعلاً:

```powershell
(Get-Content old_backup.sql) -notmatch '^(LOCK TABLES|UNLOCK TABLES)' |
    Set-Content fixed_backup.sql -Encoding utf8
```

لا تمنح `LOCK TABLES` لحلّ المشكلة؛ البرنامج لا يحتاجها في تشغيله العادي.

### الخطأ 1142 عند الاستعادة

`Error 1142 (42000) at line N: DROP command denied to user 'center_app'@'localhost'`

الاستعادة تحذف الجداول قبل إعادة إنشائها، والمستخدم لا يملك `DROP`. أضفها كما في
القسم 3 — منحة واحدة على `center_db` وحدها، لا صلاحية على مستوى الخادم. البرنامج يعرض
الأمر المطلوب داخل رسالة الخطأ نفسها.

### الخطأ 1227 عند الاستعادة

`Error 1227 (42000) at line N: Access denied; you need … privilege(s)`

يعني أن سطراً في ملف النسخة يحتاج صلاحية `SUPER` لا يملكها مستخدم القاعدة. مصدره ملف
**أُخذ بنسخة أقدم من البرنامج** على خادم مفعَّل عليه GTID (أغلب صور Docker): كان
`mysqldump` يكتب في أوله سطرَي `SET @@SESSION.SQL_LOG_BIN` و `SET @@GLOBAL.GTID_PURGED`،
وهما بيانات نسخ تماثلي لا معنى لها هنا لكن `mysql` يتوقف عندهما قبل أن يلمس أي جدول.

النسخ الجديدة لا تحوي السطرين (`--set-gtid-purged=OFF`). ولإصلاح ملف قديم احذف السطرين
منه:

```powershell
(Get-Content old_backup.sql) -notmatch '^SET @@(SESSION\.SQL_LOG_BIN|GLOBAL\.GTID_PURGED)' |
    Set-Content fixed_backup.sql -Encoding utf8
```

ثم استعد `fixed_backup.sql`. لا تمنح `SUPER` للمستخدم لحلّ المشكلة.

## 6. رصيد الطلاب — نقطة مهمة قبل التشغيل الفعلي

النظام يعمل بنموذج رصيد: الطالب يدفع في الخزينة فيزيد رصيده، وتُخصم رسوم الحصة عند
تسجيل حضوره على البوابة. **البوابة ترفض الدخول إذا لم يكفِ الرصيد.**

على تركيب جديد يبدأ كل الطلاب برصيد صفر، وهذا هو الصحيح: لا حصص محضورة ولا دفعات.
احرص على تحصيل الاشتراكات من شاشة الخزينة قبل أول يوم دراسي، وإلا سيُرفض كل الطلاب
على البوابة.

حقل `ledger_start_date` في جدول `center_settings` يُترك فارغاً (`NULL`) في التركيب
الجديد، ومعناه «احتسب كل الحركات». لا تلمسه إلا في حالة الترحيل الموصوفة أدناه.

## 7. قاعدة بيانات أُنشئت قبل اعتماد Flyway

ينطبق فقط لو كانت لديك قاعدة بيانات أنشأها إصدار قديم بـ `ddl-auto=update`، وفيها
بيانات حقيقية لا يمكن حذفها.

الإعداد `spring.flyway.baseline-on-migrate=true` يعلّم القاعدة القائمة كأنها عند
الإصدار 1 دون إعادة إنشاء الجداول، فلا يُنفَّذ `V1` عليها. لكن هذا **يفترض أن مخططها
يطابق `V1` فعلاً**. إن كان قد أُنشئ قبل تحويل المبالغ إلى `DECIMAL` فلن يطابق،
وسيرفض Hibernate بدء التشغيل برسالة تذكر العمود المختلف.

في تلك الحالة عدّل الأعمدة يدوياً لتطابق `V1` قبل التشغيل. واقرأ هذه التحذيرات
قبل كتابة أي `ALTER`:

**أوامر DDL في MySQL تُحدث commit ضمنياً.** لا يمكن لفّها في transaction والتراجع
عنها. لو نجح أمر وفشل التالي تبقى القاعدة في حالة نصف مُرحَّلة، فالنسخة الاحتياطية
هي وسيلة الرجوع الوحيدة.

**تغيير `DOUBLE` إلى `DECIMAL` يعيد بناء الجدول كاملاً** ويأخذ قفلاً يمنع الكتابة
طوال العملية. **أغلق البرنامج على كل الأجهزة** قبل البدء، ونفّذ خارج ساعات العمل.

**`ADD COLUMN IF NOT EXISTS` غير مدعومة في MySQL** (صياغة MariaDB). افحص وجود العمود
باستعلام على `INFORMATION_SCHEMA` قبل الإضافة.

**القيم المخزَّنة كـ `DOUBLE` تحمل انحرافاً**، والتحويل إلى `DECIMAL(12,2)` يقرّبها.
راجع الأرصدة والإجماليات بعد الترحيل وقارنها بما قبله.

**الدفعات القديمة ليست لها قيود خصم مقابلة**، لأن نموذج الرصيد لم يكن موجوداً. لو
احتُسبت كما هي ظهر كل طالب دائناً بمبلغ وهمي كبير ودخل مجاناً. اضبط
`center_settings.ledger_start_date` على تاريخ بدء العمل بالنظام الجديد لتصفير ما
قبله، وابدأ التحصيل من جديد.

الخطوات بالترتيب:

```bash
mysqldump -u center_app -p center_db > before_migration.sql
```

ثم أغلق البرنامج على كل الأجهزة، ثم نفّذ التعديلات على `transactions.amount` و
`course_groups.session_price` و `teachers.commission_value`، ثم أضف
`ledger_start_date` واضبطه، ثم تحقق:

```sql
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = 'center_db'
  AND COLUMN_NAME IN ('amount', 'session_price', 'commission_value');
```

يجب أن تظهر الثلاثة `decimal(12,2)`.

## 8. بناء نسخة للتوزيع

```bash
powershell -ExecutionPolicy Bypass -File packaging\build-installer.ps1
```

ينتج مجلداً في `target/installer/CenterManagement` فيه `CenterManagement.exe`
و**Java مدمجة بداخله** (نحو 240 ميجابايت). جهاز العميل لا يحتاج تثبيت Java ولا Maven —
انسخ المجلد وشغّل الملف التنفيذي.

لمثبِّت ويندوز حقيقي بأيقونة وقائمة ابدأ:

```bash
powershell -ExecutionPolicy Bypass -File packaging\build-installer.ps1 -Type msi
```

يتطلب [WiX Toolset 3.x](https://github.com/wixtoolset/wix3/releases) مثبَّتاً مسبقاً.

**متغيرات الاتصال مطلوبة على جهاز العميل** كما في القسم 3؛ التطبيق المحزوم يقرأها من
بيئة المستخدم تماماً كالتشغيل من المصدر.

## 9. تطوّر المخطط بعد التوزيع

المخطط تديره Flyway: كل تغيير هو ملف `V<رقم>__وصف.sql` في `src/main/resources/db/migration`
يُنفَّذ مرة واحدة ويُسجَّل في جدول `flyway_schema_history`. بهذا تعرف أي تركيب على أي
إصدار، ويرقّي التطبيق نفسه قاعدة العميل عند أول تشغيل بعد التحديث.

قاعدتان لا تُخالَفان:

**لا تعدّل ملف ترحيل طُبِّق على أي قاعدة.** Flyway يحفظ بصمة لكل ملف ويرفض التشغيل
عند تغيّرها. أي تعديل يكون في ملف جديد.

**ولّد المخطط ولا تكتبه يدوياً.** بعد تغيير أي كيان:

```bash
mvn -o test -Dtest=SchemaScriptGenerator
```

يكتب `target/schema-mysql.sql` من الكيانات نفسها؛ قارنه بالترحيلات الحالية وأضف
الفروق في ملف `V` جديد. المخطط المكتوب يدوياً يختلف عمّا يتوقعه Hibernate بفروق دقيقة
لا تظهر إلا عند رفض `validate` بدء التشغيل على جهاز العميل.
