# دليل نشر الخادم

`docs/first-install.md` يصف **تركيب** البرنامج على جهاز في سنتر. هذا الملف يصف **نشر**
`center-web`: خادمٌ يُقلع على منفذ بدل نافذة، ويخدم شاشات السنتر في المتصفح.

> **الاثنان يتقاسمان طبقة الأعمال نفسها ولا يعرف أحدهما الآخر.** فما في `first-install.md`
> عن المخطط والصلاحيات والنسخ الاحتياطية يبقى صحيحاً هنا، وما يختلف هو ما يلي.

---

## 1. الشكلان، والمفتاح بينهما

| | **خادمٌ لسنترٍ واحد** | **منصةٌ لعدّة سناتر** |
|---|---|---|
| `CENTER_TENANCY_ENABLED` | `false` (الافتراضي) | `true` |
| قواعد البيانات | قاعدةٌ واحدة، كالجهاز تماماً | قاعدةٌ لكل سنتر + `center_platform` |
| حقل «السنتر» في شاشة الدخول | **يُتجاهل** | يُطابَق على `slug` |
| `/api/platform` | يردّ ولا سناترَ فيه | فتحُ السناتر وإيقافُها وفوترتُها |
| صلاحيات مستخدم MySQL | على قاعدةٍ واحدة | **`CREATE` على الخادم كلِّه** — القسم 4 |

**الشكل الأول نشرٌ حقيقي لا حالةٌ اختبارية**: سنترٌ يريد شاشاته على شبكته دون أن ينضمّ
إلى منصة. ولذلك الشرطان في الكود (`SingleCentreConfig` و`PlatformCentreConfig`) مرآةُ
أحدهما للآخر، لا `@ConditionalOnMissingBean` يتغيّر جوابُه بترتيب قراءة الإعدادات.

## 2. المتطلبات

| المكوّن | أين | ملاحظة |
|---|---|---|
| Java | على الخادم | 21 — للتشغيل وحده |
| Maven | على آلة البناء | 3.9+، غير مطلوب على الخادم |
| MySQL | 8.0+ | |
| `mysqldump` و `mysql` | **على الخادم نفسه** | تُشغَّلان عند كل نسخة احتياطية |
| وسيطٌ عكسي يُنهي TLS | أمام الخادم | كوكي الجلسة `Secure` افتراضاً — القسم 7 |

**الثالث هو ما يُنسى في حاوية نحيفة.** الخادم يأخذ النسخ بتشغيل `mysqldump` عمليةً
خارجية، وصورةٌ فيها JRE وحده تُقلع وتعمل وتخدم الطلبات — ثم تفشل كلُّ نسخة ليلية.
إن لم تكن الأداتان في `PATH` فاضبط `CENTER_BACKUP_MYSQL_BIN_DIR` على مجلَّدهما: الخادم
**لا يبحث عنهما** في مسارات معروفة كما يفعل الجهاز، لأن صورةَ الخادم يبنيها من ينشرها
فمسارُ الأدوات فيها إعدادٌ يُكتب مرة لا شيء يُخمَّن عند كل نسخة.

ولا خطوةَ بناءٍ ثانية: الصفحة تحت `resources/static/` بلا npm ولا حزمٍ، والخطوط
والقوالب داخل الحزمة.

## 3. البناء والتشغيل

```bash
mvn -o install -DskipTests      # مرة، وبعد كل تغيير في center-core أو center-app
mvn -pl center-web package
java -jar center-web/target/center-web-1.0.0.jar
```

الناتج حزمةُ Boot واحدة (نحو 84 ميغابايت — JasperReports وخطوطُه فيها). وهي تُنسخ إلى
الخادم وتُشغَّل، بخلاف الجهاز الذي يُبنى له مثبِّت بـ jpackage: الخادمُ يُنشَر ولا
يُركَّب على سطح مكتب أحد.

`packaging/build-installer.ps1` يبني `-pl center-desktop -am`، فـ`center-web` خارج ذلك
المفاعل ولا أثرَ لأحدهما في الآخر.

## 4. قاعدة البيانات والصلاحيات

### خادمٌ لسنترٍ واحد

نفسُ ما في `first-install.md` §2–3 حرفاً بحرف: قاعدةٌ واحدة، ومستخدمٌ مقصورٌ عليها،
و`DROP` من أجل الاستعادة. لا جديد.

### منصة — وهنا الفرق الذي يُوقع

فتحُ سنتر ينفّذ `CREATE DATABASE` **باتصال التطبيق نفسه** (`TenantProvisioning`)،
لا باتصالٍ إداري منفصل. فمستخدم MySQL الذي يعمل به الخادم يحتاج صلاحيةً على مستوى
الخادم لا على قاعدة:

```sql
CREATE USER 'center_app'@'%' IDENTIFIED BY 'كلمة-قوية';

-- على الخادم كلّه لا على قاعدةٍ بعينها: قاعدةُ السنتر لم تُخلق بعد حين يُمنح هذا،
-- و CREATE على المستوى العام هو ما يُجيز CREATE DATABASE
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES
  ON *.* TO 'center_app'@'%';
```

`DROP` هنا لنفس سبب وجوده على الجهاز: الاستعادةُ تستبدل الجداول فتحذفها أولاً.

> ⚠️ **هذه صلاحيةٌ أوسع بكثير مما يأخذه الجهاز، وذلك ثمنُ التزويد الآلي.** إن كان فتحُ
> السناتر عندك عملاً نادراً يقوم به إنسان، فالأضيقُ والأسلم: امنح مستخدمَ التطبيق
> صلاحياتِ الجداول على القواعد القائمة وحدها، وأنشئ قاعدةَ كل سنتر يدوياً بحسابٍ إداري
> قبل استدعاء `POST /api/platform/centres`. لكن انتبه: `TenantProvisioning` ينفّذ
> `CREATE DATABASE` بلا `IF NOT EXISTS` عمداً — قاعدةٌ موجودة باسم سنترٍ جديد تُوقف
> الفتحَ بدل أن تُكتب فوق بيانات غيره — فالمسارُ اليدوي يحتاج تعديلاً في الكود، لا
> إعداداً. اطلبه إن أردته.

### قاعدة المنصة

`center_platform` قاعدةٌ مستقلة تحمل سجلَّ «من هي السناتر وأين قاعدةُ كلٍّ منها»، ولها
متغيّراتُ اتصالها الخاصة (القسم 5). وهي مستقلةٌ عمداً: وضعُ الجدول داخل أحد السناتر
يجعل سنتراً يملك قائمة جاراته.

أنشئها فارغةً؛ الترحيلاتُ تبني جداولها عند أول إقلاع:

```sql
CREATE DATABASE center_platform CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

**ولا يمكن لسنترٍ أن يحمل اسمها.** `SchemaName` يحجز `center_platform` مع قواعد MySQL
نفسها (`mysql`, `information_schema`, `performance_schema`, `sys`) — سنترٌ يأخذ ذلك
الاسم يكتب في سجلّ من هي السناتر.

## 5. متغيّرات البيئة

**كل سرٍّ يُقرأ من البيئة، ولا سرَّ في `application.properties`** — الملف متتبَّع في
git، والصورةُ تُبنى مرة وتعمل في أماكن مختلفة بأسرار مختلفة.

### الأساس

| المتغيّر | الافتراضي | ماذا يقرّر |
|---|---|---|
| `PORT` | `8080` | منفذ الخادم |
| `DB_URL` | `jdbc:mysql://localhost:3306/center_db?sslMode=REQUIRED&serverTimezone=UTC` | على المنصة: اتصالُ الخادم، وقاعدةُ السنتر تُبدَّل عليه عند كل طلب |
| `DB_USERNAME` | `center_app` | |
| `DB_PASSWORD` | — | مطلوب؛ غيابُه يُسقط الإقلاعَ برسالةٍ تسمّيه |
| `CENTER_TENANCY_ENABLED` | `false` | الشكل: سنترٌ واحد أم منصة |
| `CENTER_SETUP_TOKEN` | — | برهانُ تهيئة المدير الأوّل على خادمٍ لسنترٍ واحد — القسم 8 |
| `CENTER_COOKIE_SECURE` | `true` | كوكي الجلسة `Secure` — القسم 7 |
| `CENTER_FORWARDED_HEADERS` | `NONE` | `NATIVE` خلف وسيطٍ تملكه فقط — القسم 7 |

### المنصة وحدها

| المتغيّر | مطلوب | ماذا يقرّر |
|---|---|---|
| `CENTER_TENANCY_PLATFORM_URL` | ✅ | اتصالُ `center_platform`. غيابُه يُسقط الإقلاع برسالةٍ تسمّيه |
| `CENTER_TENANCY_PLATFORM_USERNAME` | ✅ | |
| `CENTER_TENANCY_PLATFORM_PASSWORD` | ✅ | |
| `CENTER_FLYWAY_ENABLED` | ✅ `false` | **القسم 6 — لا شيء يفرضه** |
| `CENTER_PLATFORM_TOKEN` | ✅ | رمزُ المشغّل الذي يحرس `/api/platform` |

**`CENTER_PLATFORM_TOKEN` ليس حساب مستخدم.** مشغّلُ المنصة ليس في أيّ سنتر — هو من
يفتحها — فلا صفَّ له في أيّ جدول `users` ولا جلسةَ سنترٍ تحمله. ولّده عشوائياً:

```bash
openssl rand -base64 32
```

**وغيابُه يمنع ولا يسمح.** نشرٌ نُسي فيه المتغيّر لا يفتح سناترَ لأحد، بدل أن يفتحها
للجميع — والثاني بابٌ لا يعرف أحدٌ أنه مفتوح، لأن كل شيءٍ يبدو عاملاً.

### النسخ الاحتياطية والرسائل

| المتغيّر | ماذا يقرّر |
|---|---|
| `CENTER_BACKUP_PASSPHRASE` | كلمةُ تشفير النسخ. **غيابُها يعني بلا تشفير** — لا مفتاحَ منفصل |
| `CENTER_BACKUP_ROOT` | جذرُ النسخ على القرص؛ فارغٌ يعني بلا حدّ. **اضبطه على خادم**: هو ما يحصر مسارَ النسخ الحرّ داخل مجلَّد السنتر |
| `CENTER_BACKUP_MYSQL_BIN_DIR` | مجلَّد `mysqldump`/`mysql` إن لم يكونا في `PATH` |
| `CENTER_BACKUP_OFFSITE_URL` | مستودعٌ خارج الخادم تُرفع إليه النسخة — القسم 11 |
| `CENTER_BACKUP_OFFSITE_TOKEN` | رمزُه. **عنوانٌ بلا رمزٍ عطلٌ لا إعدادٌ ناقص** |
| `CENTER_MESSAGING_TOKEN` | رمزُ مزوّد الرسائل |

## 6. ⚠️ على المنصة: أطفئ Flyway الأحادية

```bash
CENTER_FLYWAY_ENABLED=false
```

حين تُشغَّل تعدّدية المؤسسات تتولى `TenantMigrations` ترحيلَ **كل** قاعدة سنتر عند
الإقلاع. و`spring.flyway` الأحادية تبقى مُشغَّلة ما لم تُطفأ بيدك — **لا شيء في الكود
يطفئها** — فتترحّل على القاعدة التي يسمّيها `DB_URL`، أي تبني مخطّطَ سنترٍ كاملاً في
قاعدةٍ ليست سنتراً، وتترك `flyway_schema_history` فيها يرتبك عندها أول ترقية حقيقية.

## 7. خلف وسيطٍ عكسي

### الكوكي والتشفير

كوكي الجلسة `Secure` افتراضاً، فلا يُرسله المتصفح على `http` الصريح. **والنتيجة على
نشرٍ بلا TLS أن الدخول ينجح ثم يُطرَد صاحبه فوراً، ولا شيء يقول لماذا** — الخادم يردّ
صحيحاً والمتصفح لا يعيد الكوكي. ضع TLS على الوسيط، ولا تضبط `CENTER_COOKIE_SECURE=false`
إلا في تجربةٍ محلية.

### عنوان العميل

```bash
CENTER_FORWARDED_HEADERS=NATIVE     # خلف وسيطٍ تملكه، وحدها
```

`EdgeThrottle` يقفل عنواناً بعد ثلاثين محاولة دخول فاشلة — وهو الحاجز الذي يرى ما لا
تراه الخدمة: كلمةٌ واحدة شائعة على ألف اسم، حيث لا يبلغ أيُّ حساب خمسَ محاولات.

- **بلا هذا الإعداد خلف وسيط**: كلُّ الطلبات تبدو من عنوان الوسيط، فمهاجمٌ واحد يستنفد
  عدّاد الجميع. والعتبة سخيّة (ثلاثون لا خمسة) بحيث يبقى هذا إزعاجاً نادراً لا قفلاً
  جماعياً — لكنه يبقى خطأً.
- **ومع هذا الإعداد بلا وسيط**: `X-Forwarded-For` ترويسةٌ يكتبها من يطلب، فالتهرّبُ من
  الحاجز يصير سطراً في الطلب، ويصير قفلُ عنوان إنسانٍ آخر ممكناً.

اضبطه **إن وإنما إن** كان أمام الخادم وسيطٌ تملكه يمحو الترويسة ويعيد كتابتها.

### بثُّ التنبيهات

`GET /api/alerts/stream` اتصالُ SSE مفتوحٌ حتى ساعة. اطلب من الوسيط ألا يخزّنه مؤقتاً
وألا يقطعه:

```nginx
location /api/alerts/stream {
    proxy_pass http://127.0.0.1:8080;
    proxy_buffering off;
    proxy_read_timeout 3700s;
}
```

بدون `proxy_buffering off` تصل التنبيهات دفعةً واحدة عند إغلاق الاتصال — أي بعد ساعة.

### قاعدةٌ عبر الشبكة

`sslMode=REQUIRED` في `DB_URL` لا `PREFERRED`: الثانية تقبل الاتصالَ الصريح بصمت إن لم
يعرض الخادم تشفيراً. الافتراضُ المشحون في الملف `REQUIRED` أصلاً — لا تُرجعه.

## 8. أول دخول: من أين يأتي حساب المدير

### على المنصة

من رمز الدعوة. `POST /api/platform/centres` يردّ الرمزَ **مرةً واحدة** — لا يُخزَّن إلا
بصمتُه — ويُسلَّم لصاحب السنتر خارج القناة، ثم يفديه هو:

```bash
curl -X POST https://<الخادم>/api/platform/invites/redeem \
     -H 'Content-Type: application/json' \
     -d '{"code":"<الرمز>","password":"<كلمة المدير>","confirmation":"<نفسها>"}'
```

الحسابُ الناتج اسمُه `admin`. وعلى خادم، «جدولُ المستخدمين فارغ» لم يعد دليلاً على
الملكية: يكفي أن يعرف أحدٌ اسمَ السنتر ليصل إلى جدولٍ فارغ.

### على خادمٍ لسنترٍ واحد

من `CENTER_SETUP_TOKEN`. اضبطه قبل التشغيل:

```bash
CENTER_SETUP_TOKEN=$(openssl rand -base64 32)
```

ثم افتح الخادم في المتصفح: قاعدةٌ بلا حساب تعرض **شاشة التهيئة** بدل شاشة الدخول —
الرمز وكلمة المرور وتأكيدها — ويُنشأ `admin`. أو من السطر مباشرةً:

```bash
curl -X POST https://<الخادم>/api/setup \
     -H "Authorization: Bearer $CENTER_SETUP_TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"password":"<كلمة المدير>","confirmation":"<نفسها>"}'
```

**وبرهانان لا واحد، وكلٌّ منهما وحده ثقب:**

- **الرمزُ وحده** بابُ إنشاءٍ دائم لمن قرأ متغيّرات التشغيل — وهي تُقرأ في ملف خدمة وفي
  سجلّ نشر. ولذلك يبقى فحصُ **فراغ جدول المستخدمين** شرطاً معه: بعد أوّل حساب تُردّ
  النقطة بـ`409` ولو كان الرمز صحيحاً.
- **والفراغُ وحده** يجعل أوّلَ من يبلغ المنفذ مديرَ السنتر. على جهازٍ في سنتر الفراغُ
  برهانٌ كافٍ — من يجلس أمام الجهاز الذي يحمل القاعدة هو صاحبها — **وعلى خادمٍ لا يبرهن
  شيئاً**. وهو نفسُ السطر الذي وُجدت رموزُ الدعوة على المنصة لأجله؛ والمنطق لا يتغيّر
  بعدد السناتر.

**ونشرٌ بلا الرمز لا يُهيَّأ من الويب أصلاً** — لا يُفتح لمن سبق. الشاشةُ تقول ذلك
صراحةً بدل أن تعرض نموذجاً يُرفض كلُّ ما يُرسَل منه، لأن العطبَ في بيئة الخادم ولا شيء
يكتبه من يجلس أمام الشاشة يُصلحه.

ومن يبدأ من قاعدةٍ قائمة — سنترٌ يضيف الشاشات إلى تركيبٍ عامل — لا يمرّ بهذا أصلاً:
حساباتُه فيها، والشاشةُ تعرض الدخول.

> والنقطةُ **غيرُ موجودة على منصة**: هناك لا يُعرف أيُّ سنترٍ يُهيَّأ قبل جلسة، ورمزُ
> الدعوة — المربوطُ بسنترٍ بعينه — هو البرهان. ونقطةٌ تعمل في الشكلين ببرهانين مختلفين
> بابان تحت اسمٍ واحد.

## 9. فتح سنتر على المنصة

```bash
TOKEN=$CENTER_PLATFORM_TOKEN

# فتحُ سنتر: يُنشئ قاعدته، ويترحّل مخطّطها، ويزرع صفّ إعداداته، ويردّ رمزَ الدعوة
curl -X POST https://<الخادم>/api/platform/centres \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name":"سنتر النور","slug":"alnoor","schema":"center_alnoor"}'

# القائمة
curl -H "Authorization: Bearer $TOKEN" https://<الخادم>/api/platform/centres

# تسجيلُ دفعة: شهورٌ كاملة ولا مبلغ — السعرُ سعرُ الخطة لا سعرُ المتصل
curl -X POST https://<الخادم>/api/platform/centres/1/subscription \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"months":3}'

# إيقافٌ بقرار المشغّل — محورٌ مستقل عن حال الاشتراك
curl -X POST https://<الخادم>/api/platform/centres/1/status \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"status":"SUSPENDED"}'
```

**`schema` يُكتب ولا يُشتقّ من الاسم**: هو اسمٌ في خادم قواعد يعيش أطولَ من الاسم
التجاري، وتغييرُه لاحقاً نقلُ بيانات. وشروطُه (`SchemaName`): من 3 إلى **48** حرفاً،
يبدأ بحرفٍ لاتيني صغير، ولا يحمل إلا `a-z` و`0-9` و`_` — بقائمةِ سماحٍ لا منع، لأن هذا
هو الموضعُ الوحيد الذي يدخل فيه نصٌّ من الخارج إلى عبارة DDL.

و**48 لا 64** وهو حدُّ MySQL: أدواتُ التشغيل تُلحق باسم القاعدة لواحقَ خاصةً بها.

**وسنترٌ جديد يُفتح بلا تاريخ سداد**: الفوترةُ تبدأ بأول دفعةٍ تُسجَّل. وزرعُ تاريخِ
اليومِ مكانَها يُغلق سنتراً في منتصف تهيئته.

## 10. المراقبة: أيُّ سنترٍ أظلم

```bash
curl -H "Authorization: Bearer $TOKEN" https://<الخادم>/api/platform/operations
```

يردّ سطراً لكل سنتر: آخرُ نسخة احتياطية وهل تأخّرت، وآخرُ فحص تنبيهات وهل تأخّر،
والتنبيهاتُ الحرجة القائمة، وحالُ الاشتراك — و`needsAttention` خلاصةُ السطر في حقلٍ
واحد، **محسوبةً على الخادم** حتى لا تشتقّها شاشتان بشرطين مختلفين.

لا شاشةَ له بعد؛ وصلْه بمراقبتك ونبِّه على `needsAttention`. وثلاثةُ أشياء فيه مقصودة:

- **`SUSPENDED` لا يكون متأخّراً أبداً** — لا شيء يعمل له أصلاً، وخمسون إنذاراً كاذباً
  تعلّم المشغّلَ ألا ينظر.
- **و«مطفأ» ليس «متأخّراً»** — سنترٌ أطفأ النسخَ التلقائية اختار ذلك.
- **وسنترٌ تعذّرت قراءتُه يبقى في القائمة موسوماً** (`readable: false`)، ولا يُدّعى عنه
  شيء. حذفُ سطره يترك تسعةً وأربعين تبدو سليمة، والغائبُ هو بالضبط من كان يحتاج النظر.

وكلُّ سطر في السجلّ يحمل اسمَ سنتره (`%X{centre:-platform}`)، وما لا سنترَ له يُكتب
`platform` — الإقلاع، والترحيلات، ونقاط المشغّل نفسها.

## 11. النسخ الاحتياطية على الخادم

المجدوِلُ يحمل موعداً **لكل سنتر**: كلٌّ يختار ساعةَ إغلاق أبوابه، والحفظُ يسري على
السنتر الذي حفظ وحده.

**والنسخةُ التي تجلس على القرص نفسه ليست نسخةً احتياطية.** في سنترٍ يوجّه صاحبُ المسار
إلى فلاشةٍ أو قرص شبكة فتخرج بفعله؛ على خادمٍ يجلس الملف على القرص الذي يحمل قواعد
الخمسين، فعطبُه يأخذ الاثنين معاً. اضبط `CENTER_BACKUP_OFFSITE_URL` و`_TOKEN` ليُرفع
الملفُّ بعد كتابته، في مجلَّدٍ مستقلّ لكل سنتر.

أربعةُ أشياء تستحقّ المعرفة قبل أن تُسأل عنها:

- **العنوانُ يجب أن يكون `https` ولا يشير إلى عنوانٍ داخلي.** `OutboundUrl` يرفض
  loopback والشبكاتِ الخاصة و`169.254.169.254` (نقطةُ بيانات السحابة، وأولُ ما يُجرَّب)،
  ولا يتّبع إعادةَ التوجيه: `302` إلى عنوانٍ داخلي يحمل رمزَك إليه.
- **وفشلُ الرفع لا يُبطل النسخة ولا يُسكَت عنه**: يظهر في سطر `BACKUP_CREATED` في سجلّ
  المراقبة، وعلى الشاشة، ويُطلق `BACKUP_NOT_OFFSITE` — وهو نوعٌ مستقل عن `BACKUP_FAILED`
  لأن الأول يعني ملفاً سليماً في أسوأ موضع، والثاني يعني لا ملفَّ أصلاً.
- **وعنوانٌ بلا رمزٍ عطلٌ لا إعدادٌ ناقص.** أحدُهم كتب ذلك العنوان قاصداً.
- **والاستعادة تمرّ بـ`--one-database`**: ملفُّ سنترٍ آخر يحمل `USE` لقاعدته لا يكتب في
  هذه. على خادمٍ تجلس ملفاتُ الجميع في مكانٍ واحد، واختيارُ الخطأ نقرة.

وكلمةُ التشفير في البيئة لا في قاعدة البيانات: كلمةٌ محفوظةٌ داخل ما تحميه تُشحن مع كل
نسخة، وتضيع مع القرص الذي وُجدت النسخُ من أجله.

## 12. الترقية

1. ابنِ الحزمة الجديدة واختبرها (`mvn -o clean test` يمرّ بلا قاعدةٍ ولا أسرار).
2. **خُذ نسخةً احتياطية قبل الترقية** — الترحيلاتُ تجري عند الإقلاع.
3. أوقف الخادمَ القديم وشغّل الجديد.

الترحيلاتُ تجري تلقائياً: على سنترٍ واحد بـFlyway العادية، وعلى المنصة بـ
`TenantMigrations` على كل قاعدة. **وفشلُ سنترٍ لا يوقف البقية**: يُكتب سطرٌ باسمه
(`مؤسسات لم يكتمل ترحيل مخططها وتعمل بمخطط قديم`) ويكمل السعي. راقب ذلك السطر — سنترٌ
يعمل بمخطّطٍ قديم يسقط عند أول استعلامٍ يلمس عموداً جديداً، لا عند الإقلاع.

و`ddl-auto=validate` يعني أن المخطّطَ إن خالف الكيانات لا يُقلع الخادم أصلاً — عطلٌ
صاخبٌ عند الترقية خيرٌ من خطأٍ غامض بعد أسبوع.

## 13. مصائد

**متغيّرٌ مطلوب ومنسيّ يُسمَّى، ولا يظهر باسم عطلٍ آخر.** إقلاعٌ بلا `DB_PASSWORD`
يقف فوراً بـ:

```
DB_PASSWORD is not set, and spring.datasource.password needs it.
```

وقبل `RequiredCredentials` لم يكن يفعل: كان النصُّ `${DB_PASSWORD}` يمضي حرفياً إلى
MySQL فترتدّ `Access denied for user 'center_app'` — جملةٌ تقول «الكلمةُ خاطئة» بوضوح،
فتُرسل صاحبَها يفحص الصلاحيات ويعيد ضبط كلمةِ مرورٍ لم تكن خاطئة. **ورسالةٌ تقود إلى
المكان الخطأ أسوأ من رسالةٍ غامضة**: الغامضةُ تُبقي الباحثَ يبحث، وهذه تُقنعه أنه وجد.

**كوكي `Secure` على `http` صريح** — القسم 7. الدخول ينجح والجلسة تضيع فوراً.

**`CENTER_FLYWAY_ENABLED` منسيٌّ على منصة** — القسم 6. مخطّطُ سنترٍ كامل في قاعدةٍ ليست
سنتراً.

**`CENTER_FORWARDED_HEADERS=NATIVE` بلا وسيط** — القسم 7. التهرّبُ من الحاجز سطرٌ في
الطلب.

**حاويةٌ بلا `mysqldump`** — القسم 2. تُقلع وتعمل وتخدم، ثم تفشل كلُّ نسخة ليلية.

**المنطقةُ الزمنية واحدةٌ للمنصة كلِّها.** `TimeConfig` ينشر ساعةً واحدة، فـ«اليوم»
و«هل تأخّرت النسخة» يُحسبان بمنطقة الخادم. مع سناترَ في منطقةٍ واحدة لا أثرَ لذلك؛ ومع
اختلاف المناطق يحتاج الأمرُ ساعةً لكل مستأجر — ولم تُكتب بعد.

**ولا `actuator` ولا `/health`.** لفحص الحياة استعمل `GET /api/messages`: مفتوحٌ بلا
جلسة، ويردّ JSON، ولا يُقلع إلا وقد صحّ سياقُ Spring — فنجاحُه يقول إن الخادم حيٌّ فعلاً
لا إن المنفذ مفتوح. وهو لا يلمس قاعدةَ البيانات، فلا يكشف انقطاعَها.
