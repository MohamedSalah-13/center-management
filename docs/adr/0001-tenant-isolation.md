# ADR 0001 — عزل المؤسسات في إصدار SaaS: schema لكل مؤسسة

- **الحالة:** مقترح (يصير "مقبول" بقرار صاحب المشروع؛ لا يُبنى شيء من المرحلة 2 قبل ذلك)
- **التاريخ:** 2026-09-20
- **السياق الأوسع:** `docs/saas-review-and-plan.md` §3

## السياق

التطبيق مبني منذ يومه الأول على "مؤسسة واحدة في قاعدة واحدة"، وهذا ليس افتراضاً ضمنياً بل
مكتوب في البنية:

- صف إعدادات واحد بمعرّف ثابت (`CenterSettings.id = 1`، `SettingsService.SETTINGS_ID`)
  يقرأه 17 موضعاً.
- ستة قيود فريدة على مستوى الجدول كله: `users.username`، `students.barcode`، `students.name`،
  `alert_rules.type`، `alerts.dedupe_key`، و`center_settings` نفسه.
- النسخ الاحتياطي والاستعادة عبر `mysqldump`/`mysql` على القاعدة كاملة، بتشفير لكل ملف.
- نحو 40 من 69 استعلاماً معلناً تجمع على الجدول كله (أرصدة، متأخرات، سجل المراقبة، علامة
  استطلاع التنبيهات)، إضافة إلى ~10 استدعاءات `findAll()` في الخدمات.
- سجل المراقبة وجدول التنبيهات بلا أي عمود نطاق، ومفتاح إزالة التكرار في التنبيهات مبني من
  `type:entity:window` فقط.

المطلوب تشغيل نفس طبقة الأعمال لعشرات إلى مئات السناتر على خادم واحد، مع بقاء إصدار
سطح المكتب يعمل على قاعدة محلية بلا تغيير في سلوكه.

## الخيارات

### أ. schema لكل مؤسسة (Hibernate `SCHEMA` multitenancy)

قاعدة MySQL واحدة تحمل schema لكل مؤسسة (`center_t0001`…) وschema منصة (`center_platform`)
للمؤسسات وحسابات الدخول وحالة الاشتراك. Hibernate يوجّه كل اتصال إلى schema المؤسسة الحالية
عبر `CurrentTenantIdentifierResolver` يقرأ `TenantContext` الموجود أصلاً في `center-core`.

### ب. قاعدة مشتركة مع عمود `tenant_id`

كل جدول تشغيلي يحمل `tenant_id`، وكل استعلام يقيَّد به (عبر `@TenantId` أو `@Filter` أو
يدوياً)، وكل قيد فريد يُوسَّع إلى `(tenant_id, …)`.

## المقارنة

| | أ. schema لكل مؤسسة | ب. قاعدة مشتركة |
|---|---|---|
| تغييرات الاستعلامات | لا شيء | ~40 استعلاماً + 10 `findAll` + كل استعلام مستقبلي |
| القيود الفريدة الستة | تبقى | تُوسَّع كلها، و`dedupe_key` يعاد تركيبه |
| `center_settings`, `alert_rules` | تبقى (صف لكل schema) | إعادة تصميم |
| النسخ الاحتياطي والاستعادة | `mysqldump` لكل schema، الكود الحالي يكاد يعمل كما هو | تصدير مُرشَّح: إعادة كتابة |
| استعلام منسي بلا نطاق | لا يرى schema أخرى | تسرب بيانات بين مؤسستين |
| Desktop | نفس الكود وschema واحد | نفس الكود مع `tenant_id = 1` في كل مكان |
| الترقية | Flyway على N schema في حلقة | Flyway مرة واحدة |
| تقارير عبر المؤسسات | صعبة (استعلام على schema متعددة) | سهلة |
| عدد المستأجرين الذي يبدأ يؤلم | آلاف (عدد schema وconnection pools) | لا حد عملي |

## القرار المقترح

**الخيار أ.** السبب الحاسم ليس حجم العمل وحده بل نوع الخطر: في (ب) كل استعلام يُكتب مستقبلاً
هو فرصة تسرب بين مؤسستين لا يكشفه اختبار عادي، بينما في (أ) الخطأ الوحيد الممكن هو في طبقة
توجيه الاتصال، وهي مكان واحد يُختبر مرة واحدة. والسوق المستهدف — سناتر تعليمية، كل منها
بياناته مستقلة ولا يحتاج تقارير مع غيره — لا يستفيد من ميزة (ب) الوحيدة.

## النتائج

**ما يتغير:**

- جدول `tenants` (وحسابات دخول المنصة لاحقاً) ينتمي إلى `center_platform`، لا إلى schema
  المؤسسة. `V16` أنشأه داخل schema التطبيق ولا يُعدَّل (قد يكون طُبّق)، لكن لا يُبنى فوقه هناك؛
  `branches` ينتمي فعلاً إلى schema المؤسسة ويبقى.
- تزويد مؤسسة جديدة = إنشاء schema + تشغيل Flyway عليه + صف `center_settings` + المدير الأول
  عبر رمز دعوة (يستبدل شرط `userRepository.count() == 0`).
- عند الإقلاع أو النشر: حلقة Flyway على كل schema نشط، مع تسجيل ما فشل وعدم إيقاف الباقي.
- المجدولون (`BackupScheduler`, `AlertScheduler`) يدورون على المؤسسات النشطة ويضبطون
  `TenantContext` لكل دورة؛ `AlertFeed` يُفتاح بالمؤسسة والجلسة.
- النسخ الاحتياطي لكل schema، والاستعادة مقيدة باسم schema المؤسسة (`--one-database`).
- سطح المكتب: `TenantId.DESKTOP` وschema واحد، بلا تغيير في الكود المشترك.

**ما لا يتغير:** كل الاستعلامات، كل القيود الفريدة، الكيانات، ترحيلات V1..V16، سلوك Desktop.

**ما يجب الانتباه له:**

- `useSSL=false` وكلمة مرور فارغة افتراضياً في `application.properties` غير مقبولين على
  خادم مشترك بغض النظر عن الخيار (راجع الخطة §2.4).
- المستخدم الواحد من MySQL للمنصة يحتاج صلاحية إنشاء schema، وهذا أوسع من مستخدم Desktop
  محدود الصلاحيات في `docs/first-install.md`؛ يُفصل مستخدم التزويد عن مستخدم التشغيل.
- `MySqlMigrationIntegrationTest` يجب أن يُمدَّد لاختبار مؤسستين: عملية في الأولى لا تظهر في
  الثانية (مجدول، تنبيه، تقرير).

## متى يُعاد النظر

إذا تجاوز عدد المؤسسات النشطة الألف، أو ظهرت حاجة حقيقية لتقارير عبر المؤسسات، أو انتقلت
المنصة إلى قاعدة لا تدعم توجيه schema بكلفة رخيصة. حينها يكون الانتقال إلى (ب) ممكناً لأن
كل schema هو نفس المخطط: إضافة `tenant_id` وحقنه من اسم schema المصدر عملية آلية.
